# Git、GitHub 和 commit 怎么用

把它们分成三件事就够了：

- **Git**：本机的版本记录系统。可以比较文件、找回旧版本、看一段代码什么时候改的。
- **GitHub**：托管 Git 仓库的网站，也是别人浏览、下载和参与项目的入口。推送之后，GitHub 上就有一份同步的仓库。
- **commit**：Git 里一个带说明的存档点。它不是另一份日志，也不需要每改一行就提交。

## 这个仓库分别负责什么

| 地方 | 放什么 | 不放什么 |
|---|---|---|
| GitHub 项目页 | 项目介绍、怎么运行、现在做到哪、下一步 | 每次改动的逐条流水账 |
| Git commit | 一组有意义的代码或文档变化 | 为了凑次数拆出来的空提交 |
| README.md | 当前状态和新读者入口 | 旧阶段的待办、完整失败过程 |
| docs/ | 学习笔记、项目计划、实验结论、代码地图 | 每个 commit 的副本 |
| docs/archive/ | 偶尔需要回查的旧交接稿和旧时间线 | 当前状态的权威答案 |

## 什么时候提交

等一个改动已经有一个说得清的结果时再提交，比如“视觉位姿接入抓取流程”或“修正卡盘孔径并重跑判据”。可以把相关代码、测试和必要的说明放在同一个 commit。

不必遵守“每次提交只改一个文件类型”或“每次都写长正文”。一个简单的标题足够说明结果；若原因不明显，再补一两句背景。

提交前至少看：

```bash
git status
git diff
python verify_all.py
```

如果只是试验、还没确定方向，可以先不提交；也可以在本地做临时 commit，之后整理。Git 不会因为提交多就自动变好，重点是能看懂、能回退。

## 常用查看方式

```bash
git status --short
git log --oneline -10
git show <commit>
git diff
```

GitHub 的 `main` 是目前推上去的版本；历史 commit 可以在 GitHub 页面或本地用 `git log` 查看。日常不需要把 commit hash 抄进 README。

## 够用的提交标题

```text
修正卡盘通孔并重跑变径检查
增加视觉位姿输入
整理项目学习入口
```

标题写做了什么即可。除非这次改动有不容易从 diff 看出的决定，否则不需要模板、表格或单独的 commit 文件。
