# P5.8.18：抓取前点头角度定义与约束试验

日期：2026-11-10

## 本卡回答的问题

用户看到机械臂在夹料前“点头”。本卡把画面问题和仿真轨迹问题分开：

1. 实时画面为什么会瞬移？
2. 单次抓取轨迹里的夹爪为什么会向下转？
3. 能不能只把向下角度锁住，同时保留正确抓取？

所有轨迹结论均来自 MuJoCo 仿真，不代表真机表现。

## 画面瞬移：循环重置，不等于单次轨迹点头

检查时发现两个 `live_bridge.py run --loop` 进程，以及两个只读 `view` 进程。`run --loop` 每轮都会重新创建模型和 `MjData`，完整送料结束后会回到初始关节姿态再开始下一轮；循环边界的状态跳变会被窗口直接显示成“瞬移”。两个循环发送进程已停止，查看窗口保留，但不会再接收新帧。

`src/live_bridge.py` 的本地未提交改动已有发送端互斥锁，能阻止另一个新发送端取得发布权；互斥锁不能修复循环回起点的跳变，也不能让已经运行的旧进程自动加载新代码。观察单次动作时应运行 `python src/live_bridge.py run`，不要加 `--loop`。

## 点头基线：IK 规划姿态本身在向下转

测量定义：取 `gripperframe` 局部 `+X` 作为夹爪前向轴，计算它相对水平面的向下角度，向下为正。由 P5.8.18 基线逐步四元数离线计算：

| 动作段 | 计划向下角：起点 → 终点 | 计划向下角范围 | 完整姿态最大转角 | 实际位置最大跟踪差 |
|---|---:|---:|---:|---:|
| 接近 | `11.82° → 30.42°` | `20.58°` | `35.49°` | `24.90 mm` |
| 侧向进入 | `31.06° → 50.07°` | `19.02°` | `19.33°` | `14.77 mm` |

实际夹爪姿态基本跟着计划走：接近段最大姿态跟踪误差 `4.30°`，侧向进入 `2.82°`。这说明主要原因是**位置 IK 只要求夹爪到达位置、没有指定这段该保持什么姿态**，求解出来的计划姿态自然发生变化；这不是工件碰撞造成的，也没有证据支持把它单纯归咎于伺服振荡。跟踪位置差较大，会让画面显得迟滞，但并非计划点头的来源。

基线完整送料按当前项目判据 `PASS`：同轴 `0.519 mm`、最终倾角 `1.445°`、卡爪接触点 `30`、余量偏心 `1.141 mm`、抓取时倾角差 `1.870°`。这是同一固定名义工况的一次仿真，不是普遍成功率。

## 单角度约束试验：角度变稳，但抓取姿态坏了

临时试验在接近和侧向进入的 8 个笛卡尔路点上，增加一个约束：夹爪前向轴的向下角度保持在动作起始角，同时 `wrist_roll` 仍锁在抓取设定值。结果：

- 接近向下角变化范围从基线 `20.58°` 降到 `0.73°`；侧向进入从 `19.02°` 降到 `0.57°`。
- 但只约束这一个角度，夹爪其余方向可以转到不合适的位置。下降到工件后抓取倾角差变为 `43.87°`，V 爪有效接触只有 `4` 点。
- 后续搬运大幅偏离，三爪接触为 `0`，送料结果 `FAIL`；仿真还报告 `QACC` 数值不稳定。

因此“夹爪前向轴一直水平/不点头”不是正确的独立目标。它改善了单项角度，却破坏了抓取所需的整体方向。临时求解代码已移除，没有进入默认流程；候选 JSON 留在本地忽略目录 `_build/p5.8.18-arm-pitch/`。

## 当前结论与下一步

目前已经知道：

1. 画面瞬移来自循环发送流程回到初始状态；循环发送器已停。
2. 抓取前的“点头”来自姿态约束不足：当前 IK 以位置为主，允许夹爪姿态变化；实际姿态大体跟随该计划。
3. 单独压住一个俯仰量会损坏夹爪的其他方向，不能作为修复。

下一卡 P5.8.19 应先从通过的 nominal 抓取末端姿态提取真正必要的夹爪方向约束，再生成从当前位置到该抓取姿态的连续进场路径。先用“抓取后停止”的诊断检查棒料轴线、V 爪接触数量及位置误差；这些通过后再跑完整送料。只有俯仰变化下降、抓取接触不退化、没有数值不稳定，且完整送料仍 `PASS`，才考虑进入默认流程。
